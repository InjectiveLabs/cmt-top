# cmt-top capacity plan: 100–150 concurrent users

Reviewed 22 September 2026 against application commit `52532c264714ce5fd7c10ab2e44c335e4a4fdbcc` and the running mainnet/testnet deployments. This document records the pre-implementation assessment. See the implementation backlog and testing results for subsequent changes and validation.

For implementable work packages, file ownership, implementation roles and execution order, use the [implementation backlog](CAPACITY_IMPLEMENTATION_PLAN.md).

**Recommendation:** target 150 active browser sessions per environment on one optimized cmt-top pod, with a tested burst to 200. Keep the shared chain collector and reduce repeated serialization, streaming, and investigation work. Release only after realistic replay passes the gates below. Single-pod capacity is a hypothesis to validate, not an established result.

Count browser tabs, not registered users. The base target assumes one active tab per person. Test 150 active plus 150 hidden tabs separately before claiming support for 150 people with two connected tabs. Mainnet and testnet must pass independently.

Earlier September 18 traffic and timing measurements provide historical context; the checks below confirm baseline blockers and correct the earlier infrastructure assumptions.

**Baseline limits**

| Finding | Fresh evidence | Implication |
| --- | --- | --- |
| Hard cap of 32 browser WebSockets | Local attempts against unchanged code: 100 attempts → 32 accepted / 68 HTTP 503; 150 → 32 accepted / 118 HTTP 503. [Admission code](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/internal/web/ws.go#L24). | Neither target is currently possible, regardless of CPU. |
| API quota is 60 requests/second per socket peer IP | Local 150-request burst with one peer IP and distinct `X-Forwarded-For` values → 60 HTTP 200 / 90 HTTP 429. [API limiter](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/internal/web/server.go#L69). | Proxy traffic can share a quota; large shared-NAT audiences also need a suitable budget. |
| Repeated full dashboard delivery | Full snapshot every second **and after each subscribed non-vote event**; each client calls `WriteJSON`. [Snapshot delivery](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/internal/web/ws.go#L113), [encoding](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/internal/web/ws.go#L291). | CPU, allocation, bandwidth and browser work increase with viewers. |
| Investigation polls the entire height | A report request runs one second after the previous request completes, while the dashboard WebSocket stays connected. [Polling](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/web/src/lib/poll.ts#L23). | At 50 ms response time, 100 investigators generate about 95 report requests/s; 150 generate about 143/s. |
| Report construction shares the ingestion lock | Every request clones/groups/sorts retained rounds under the tracker read lock. [Archive read](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/internal/divergence/archive.go#L313). | Reader pressure can delay ingestion. The upstream queue holds 1,024 events and drops on overflow; viewer resync cannot recover those lost raw votes. |
| Startup and recovery amplify overload | Initial `/api/state` must succeed before connecting; failed handshakes trigger another full state read. Initial 429 stops startup pending manual retry. [Bootstrap](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/web/src/App.svelte#L75), [reconnect](https://github.com/InjectiveLabs/cmt-top/blob/52532c264714ce5fd7c10ab2e44c335e4a4fdbcc/web/src/lib/ws.ts#L73). | A direct-WebSocket test alone misses the full browser failure mode. |

Fresh synthetic archive measurements used 45 validators, both vote phases, a 30/15 hash split, 40-character addresses and 64-character hashes:

| Retained rounds at one height | Encoded archive JSON |
| ---: | ---: |
| 1 | 36,637 bytes |
| 32 | 1,156,570 bytes |
| 128 | 4,624,682 bytes |

These exclude response context and transport overhead. At a nominal one full fetch per second for 150 viewers, the 128-round case demands about **694 MB/s of payload**. That is demand arithmetic, not achieved throughput; the actual closed-loop request rate falls as latency rises. Caching construction alone does not remove these repeated response bytes.

**Deployment and constraints at assessment time**

Both environments were verified running chart `0.1.4`, one replica with `Recreate`, and image digest `ba90c2a4f3ae7730c4a5c1294c4e941086fdd539faee75402734ee1264e1a64b` (v0.1.2). Each pod requests **100m CPU / 128 MiB**, with limits of **1 CPU / 512 MiB**. Both were Ready with zero restarts. Point-in-time usage was 65m / 17 MiB mainnet and 16m / 12 MiB testnet; these readings do not establish capacity.

For isolated performance testing, start with **1 CPU / 512 MiB requested and 2 CPU / 1 GiB limited**. Select final resources from the results. Kubernetes schedules using requests, so spare observed CPU does not establish that a larger request will fit. [Kubernetes resource management](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/).

- **Asia:** all ten eligible nodes currently have only 266–766m of CPU request capacity free. The current pod's node has 666m free, or 766m after releasing its existing 100m request. A 1-CPU request cannot currently fit on an eligible node. Free reservations or add eligible capacity before rollout.
- **US:** the current node has only 476m free, but four other eligible nodes have room for at least 1 CPU / 512 MiB. Rescheduling is an available option; recheck capacity at rollout.
- **Monitoring:** SigNoz's pod discovery excludes the cmt-top namespaces, and the app has no scrape annotations. Add both namespace discovery and annotations, or an explicit scrape job. Verify one working target per pod; annotations alone will not work.
- **Gateway:** the Service uses `appProtocol: kubernetes.io/ws`, and the accepted HTTPRoute has `request: 0s`. Preserve these streaming settings. Each shared Gateway proxy has one replica and no explicit resource requests/limits; measure it alongside the app during the load test.

**Implementation plan, in release order**

1. **Make capacity measurable and reproducible.** Add browser active/rejected connections, bytes by message type, queue bytes/age, resyncs, snapshot build/encode duration, API latency/status, report cache/build statistics and ingestion lag. Keep metric labels bounded. Existing `cmt_top_ws_connected` measures the upstream chain socket. Build deterministic replay with realistic validator counts, vote/block bursts, 120 recent blocks, and stalled heights containing 1/32/128 rounds. The existing six-validator visual fixture is useful for UI checks but does not establish throughput. Record a baseline at current settings, including CPU/GC/lock profiles and Gateway traffic.

2. **Bound streaming work and raise admission together.** Add a validated connection-cap setting, exposed through TOML/environment and Helm. Start with **256 connections** for the 150-active/200-burst target; use **512 only after separately testing 300 connected tabs**. Reserve pending slots without holding broadcast locks across network handshakes. Serialize common payloads once and add each client's sequence envelope without repeatedly encoding the complete object graph. Profile remaining per-viewer byte scans/copies: wrapping cached `json.RawMessage` in `WriteJSON` still processes those bytes. Preserve baseline-first ordering, subscriptions and sequence-gap recovery. Start by coalescing ordinary full snapshots to at most one per second, retaining explicit initial/resync baselines. Bound queued bytes and age, replace obsolete snapshots, throttle/coalesce resync commands, and disconnect sustained slow readers. Benchmark optional compression after reducing redundant payloads; Gorilla supports [prepared messages](https://pkg.go.dev/github.com/gorilla/websocket@v1.5.3#PreparedMessage), but different per-client sequence numbers prevent blindly sharing complete frames.

   If the first optimization does not meet CPU/bandwidth gates, add compact state/vote batches every 100–250 ms and move full repair snapshots toward five seconds. Complete reducers for metadata, block history, errors/clears, validator changes and health first. Keep raw archived evidence intact. Test old tabs against the new server and new tabs against a rolled-back server, with explicit protocol negotiation or refresh recovery when needed.

3. **Make investigation reads shared and small.** Cache immutable report materialization and serialized evidence by height/revision, with one builder per revision and a total byte budget. Coalesce vote-burst invalidation so an active height builds at most once per 250–1,000 ms; do not rebuild separately for every viewer. Shorten time holding the ingestion lock. Return all-round summaries plus selected/comparison-round detail; move complete evidence export to an explicit request with bounded concurrency. Use revisions/conditional reads to skip unchanged data. Keep `generatedAt`, live health, changing retention context and globally derived `live`/`passed` status separate from evidence revision, or invalidate when their inputs change. Advancing the global observed/committed height can change an older report without adding votes to it. Invalidate for late/conflicting votes, roster changes, commit evidence and eviction; committed heights can still change.

4. **Make browser demand and quotas match the workload.** Stop investigation polling in hidden tabs, back off settled heights to 5–10 seconds, and add jitter/error backoff. Budget cache delay plus polling plus delivery together: active investigation evidence should reach the screen within two seconds at p95 and three seconds at p99. Adjust five-second stale indicators to the chosen cadence. Remove duplicate baseline/resume requests and replace expensive failed-handshake probes with a small status/auth response. Retry transient bootstrap failures automatically and reset reconnect backoff only after a stable connection. Batch UI updates. Give investigation pages lightweight health/context updates: removing vote subscriptions alone leaves full dashboard snapshots. Verify the actual Gateway peer/header path before enabling trusted-proxy client identification. Budget quotas for 150 users behind one NAT plus startup bursts, and separately bound expensive report/export work. Preserve existing authentication and origin behavior.

5. **Prove capacity, then roll out.** Run the following gates in an isolated deployment behind the same kind of Gateway, using replay rather than chain RPC traffic. Resolve Asia scheduling and scrape discovery first. Deploy testnet, verify live health, then mainnet outside an active investigation. Pin image digest/config/chart revision and retain the previous versions. Export needed evidence before any restart: `Recreate` and rollback both lose the process's in-memory archive. Validate advancing heights, fresh observations and ingestion lag after rollout; Ready alone only establishes initial observations.

Steps 2 and 3 can run in parallel after agreeing on the load harness and wire contracts; frontend work should track both. A rough planning allowance is **6–10 engineering days**, plus any infrastructure capacity/provisioning delay. This is an estimate, not a delivery commitment; profiling and protocol changes may alter it.

**Release gates**

| Scenario | Required result |
| --- | --- |
| Ramp 1 → 32 → 50 → 100 → 150 active tabs; hold 150 for 30 minutes | No valid-client admission or quota rejection, no unexpected disconnects; ordinary API error rate below 0.1%. |
| 200-tab burst; 150 synchronized cold starts and reconnects through a shared IP | Bounded CPU/queues, automatic recovery; at least 99% reach an authoritative baseline within 10 seconds. Test the complete browser bootstrap flow. |
| 150 investigators on the same height, then different retained heights; 1/32/128 rounds | Interactive API p95 below 250 ms and p99 below one second in-region. Active evidence freshness p95 below two seconds and p99 below three seconds. Full exports have a separate concurrency/latency budget. Evidence matches the replay oracle. |
| Fast clients mixed with throttled/non-reading clients, repeated 429/503 and flapping sockets | Healthy-client incremental vote/block delivery p95 below 500 ms and p99 below one second; snapshot-only metadata p99 below two seconds; no global resync storm; deliberate client queue loss repairs within two seconds. |
| One-hour mixed soak, upstream outage/recovery and process restart | Zero ingestion/internal-bus drops under supported load; no sustained memory growth; RSS below 70% of limit, CPU p95 below 75% of limit, CPU-throttled periods below 5%. |
| 150 active plus 150 hidden tabs | Separate connection budget passes; hidden polling stops and returning tabs refresh without losing pause/selection or misreporting freshness. |
| Protocol and evidence regressions | Both vote phases, late/conflicting observations, coverage/eviction, hash comparison, export, pause/resume and old/new client recovery remain correct. Spoofed forwarded headers cannot bypass trusted-proxy rules. |

Record both payload and actual network bytes, including the Gateway. Target at least a **75% reduction in dashboard streaming bytes** against the same replay baseline; treat this as an optimization goal, with freshness/correctness mandatory. Measure delivery and evidence freshness from server ingestion to browser reducer application, using synchronized clocks; include batching, caching and polling delay. Keep upstream subscriptions/poll rates constant as viewers increase. End-user geography adds network latency to the in-region targets.

**When to revisit the architecture**

The collector, state and observation archive are in-process. Each extra replica would collect independently and retain a different history. Keep one replica for this milestone. If an optimized pod still fails the gates, or availability through restart becomes a requirement, design one logical collector with a durable ordered event/archive store and separate fanout/API replicas. Define leadership, replay cursors and consistent archive reads before enabling replica autoscaling. HPA adjusts replica counts; the need to separate application state is an inference from cmt-top's current design. [Kubernetes HPA documentation](https://kubernetes.io/docs/concepts/workloads/autoscaling/horizontal-pod-autoscale/).

Fresh verification for this plan: isolated Go test overlays against unchanged application source, using Go 1.26.4 on darwin/arm64, reproduced admission/quota limits and archive sizes with `-count=1`. Independent backend/frontend reviews checked the code paths; deployment review used read-only cluster inspection. No production load test, application implementation, or infrastructure change was performed as part of that assessment. Sustained 150-user throughput remains to be demonstrated by the release gates.
